# 백본 트래픽 관제 · 이벤트 대비 (버전 2)

IDC 관제 2년 3개월 경험에서 손으로 반복하던 일을 자동화해 본 포트폴리오입니다.
**모든 데이터(센터, 고객사, 회선, 수치, 월드컵 일정, 서버실 온도, 방문자, 장비 출력)는 지어낸 가상 데이터입니다.** 센터 이름(분당·서초·구로·안산)은 지명만 빌린 가상 센터이며 실제 센터의 설계·장비·수치가 아닙니다. 실제 회사·고객사 자료와 실제 월드컵 일정은 쓰지 않았습니다.

배포 주소: https://traffic-event-prep.vercel.app/

## 직접 겪은 것과 가정한 것
- 직접 겪은 것: 5분 간격 그래프 확인, 데이터 내려받아 고객사에 전달, 서버 온도 체크, 육안점검(불빛 보고 판단), 방문 신청 등록, 광값·CRC 확인, 경기·행사 때 사전 연락과 분산, 새벽 DDoS 확인
- **가정한 것**
  - 하이드레이션 타임(전·후반 약 3분, 트래픽 약 20% 감소): 퇴사 후 생긴 규칙이라 직접 겪지 못했고 수치도 임의입니다.
  - 경기 시청 곡선, 배율, 고객사-회선 연결, 95%값 포함 여부
  - 랙 입구 온도 기준(27·30·33°C), 장비 LED 의미, 냉각 이상 사례

## 실행
```bash
python3 gen_data.py          # data/*.csv 생성 (seed 고정)
python3 export_site_data.py  # site/data.js 생성
cd site && python3 -m http.server 8000   # http://localhost:8000
```

## 테스트
```bash
python3 -m unittest discover -s tests -v   # 데이터 규칙 + 파이썬 교차 검증 + 정답표 최신 여부 (pandas, node 필요)
node --test "tests/*.test.js"              # 탐지 정확도(정답표 비교) + 규칙 경계값 (Node 18 이상)
node tests/report.js                       # 정답표 vs 탐지 결과를 표로 출력 (재현율·오탐)
node tests/sweep.js                        # 탐지 기준값을 바꿔 가며 놓침·오탐 변화 보기
node tests/smoke.js                        # 화면 점검 (playwright 필요, 주소를 넘기면 배포본도 점검)
python3 tests/make_truth.py                # 정답표(tests/ground_truth.json, docs/ground_truth.md) 다시 만들기
```

- 정답표: 데이터에 일부러 심은 사건이 정답입니다. 사람이 읽는 표는 `docs/ground_truth.md`입니다.
- 교차 검증: 사이트의 탐지(JavaScript)를 파이썬으로 따로 다시 계산해 같은 결과가 나오는지 비교합니다.
- 설계도 일관성: 장비·포트·연결이 서로 맞는지, 그래프 링크 15개가 모두 설계도에 있는지 확인합니다.
- 규칙 경계값: 79.9%/80.0%, 2.99배/3.0배, 10분/15분 같은 기준 바로 위·아래를 확인합니다.

## 구조
- `gen_data.py`: 가짜 데이터 생성 (평소 곡선 + 월드컵 7경기 + 새벽 급증 + 급감 2건 + 서버실 온도)
- `export_site_data.py`: CSV를 사이트용 데이터로 변환
- `site/lib.js`: 탐지·판정 규칙 (화면 코드 없음, 터미널에서도 실행)
- `site/topology.js`: 설계도 (센터·장비·랙·회선의 기준. 가상 장비 120대(Cisco 16·Juniper 34·Huawei 70)와 연결표 120여 건, 가상 고객사 13곳과 그 접속 장비. 서초에 대형 중앙 백본 2대, 센터 4개(분당·서초·구로·안산)가 거기에 이중화로 붙음, CDN 연결은 여러 곳. 분당 장비가 가장 많음. 랙 규칙: Cisco는 랙 하나를 혼자 쓰고 Juniper는 랙당 최대 2대(제가 정한 가정). 화웨이는 쓰지 않음)
- `site/`: 정적 웹페이지 (외부 라이브러리 없음)
- `tests/`, `docs/`: 데이터 규칙 검사, 탐지 정확도 시험, 화면 점검, 정답표

## 알아 둘 점
- 사후 정리의 "실제"는 분산 조치 전 가상 데이터 기준입니다.
- 내려받는 파일 이름은 영문입니다. 한글 이름이면 일부 브라우저에서 이름이 사라지는 것을 확인했습니다.
- 생성해 둔 데이터는 14일치(10/19~11/01)입니다. 월간 자료의 10/19 이전 구간(지난달 앞부분, 긴 기간 등)은 같은 규칙(평소 하루 모양)으로 화면에서 즉석에서 만든 가상 값이며, 경기·사고는 없는 평소 기록입니다.
- 이름 규칙은 `IDC_<센터 코드>_<종류><번호>`입니다. 센터 코드는 B 분당, S 서초, G 구로, A 안산이고, 종류는 FS = Juniper, FR = Cisco, AS = Huawei 계열입니다. 그래프 회선은 `IDC_B_FS1_UP1`처럼 장비와 용도가 보이게 지었습니다. 랙은 `IDC_B_R08`처럼 같은 규칙이고, 랙에는 네트워크 장비만 들어갑니다. FS·FR·AS가 무슨 약자인지는 확인하지 못했습니다.
- **센터 동기화**: 맨 위 "센터" 선택(전체·분당·서초·구로·안산)은 **관제와 서버실에서만** 보이고, 두 화면이 같은 센터로 맞춰집니다. 서버실에서만 센터 버튼 옆에 랙·장비 수가 보입니다. 터미널·설계도는 센터 선택과 상관없이 전체 장비를 보여 줍니다. 선택은 브라우저에 저장됩니다. 센터마다 보이는 그래프·랙 이름이 모두 그 센터 소속이고 설계도와 일치하는지 시험(`tests/topology.test.js`, `tests/smoke.js`)으로 확인합니다.
- 고객사 19곳(전부 가상, 이 중 큰 고객사 6곳은 서초 2·분당 2·구로 1·안산 1)과 회선 배정, 고객 접속 장비(센터마다 Juniper, 장비 하나에 1~3곳)는 제가 임의로 정한 것입니다. 센터별 장비 수(분당 FR4·FS8·AS10, 서초 FR6·FS12·AS30, 구로 FR2·FS4·AS20, 안산 FR4·FS10·AS10)는 요청받은 값이고, 랙 수는 장비 수와 랙 규칙에서 나옵니다(분당 10·서초 16·구로 8·안산 12개). 랙 규칙은 Cisco 랙당 1대, Juniper 랙당 최대 2대(요청받은 값), Huawei 랙당 최대 8대(제가 정한 가정)입니다. 모든 회선에 고객사가 하나 이상 붙어 있고, 그래프 제목은 고객사가 3곳 이상이면 "외 N곳"으로 줄여 보입니다.
- 장비 분포(센터별 장비 수는 요청받은 값, 서초가 가장 큼)와 설계도는 은호님 기억을 바탕으로 제가 만든 초안이며 현장과 다를 수 있습니다.
- 경기 중 in이 평소의 3배로 오르는 것은 알림으로 봅니다(은호님 판단: 간당간당한 수준). 경기 겹침 표시는 원인 표시입니다.
- 정답표 시험은 "깨끗한" 가짜 데이터(평소 잡음 2%)로 하므로, 탐지 기준이 느슨해도 통과합니다 (`node tests/sweep.js`로 확인). 애매한 케이스(완만한 감소, 짧은 하락, 잡음이 큰 날 등)를 추가해야 기준의 좋고 나쁨을 가릴 수 있습니다.
- 방문 등록·육안점검 기록은 브라우저(localStorage)에만 저장되며 서버로 보내지 않습니다.
- **업무 메모 반영**: 터미널의 명령어(회선 설명·로그·ARP/ping·BGP·설정 확인)와 "장애가 터졌을 때" 대응 순서(회선 확인 → 로그 → 트래픽 전/후 → 광값·CRC → IP·ping → 연동망 문의 3가지 → 문자·조장 전달)는 제 업무 메모를 일반화해 가져왔습니다. 실제 고객사 이름, 실제 IP, 내부 도구의 메뉴 경로, 장비 모델명은 쓰지 않았고, 출력의 IP(10.x)·MAC·로그·BGP 값은 모두 제가 만든 가상 값입니다. 그 순서를 따라가 보는 시나리오가 "업링크 회선 다운"입니다(데이터에 있는 안산 업링크 다운 구간 사용).
- **센터 순서와 센터 간 회선**: 센터 선택은 전체 → 서초 → 분당 → 구로 → 안산 순서입니다(코어 백본이 서초). 서초 중앙 백본에서 분당으로 들어오는 회선(`IDC_S_FS2_TOB1`, 용량 200G는 임시값)을 추가했고, 이 회선은 서초 관제와 분당 관제 양쪽에 보입니다(`feeds`).
- 큰 고객사 6곳의 이름, 전용 회선 용량(100~200G)과 피크 비율(40~55%, 피크가 수십 G)은 제가 정한 가정입니다. 한국 사업자의 실제 스트리밍 트래픽 수치는 공개 자료에서 찾지 못했습니다.
- **이중화와 회선 밀도**(제가 만든 가상 값): 모든 장비는 번호 순서대로 둘씩 짝(FS1-FS2, FR1-FR2, AS1-AS2 ...)이고 서로 연결(`_PAIR1`)되며, 센터 백본 짝 두 대에 각각 업링크가 붙습니다. 장비마다 고객 회선(1G·10G)이 한 줄씩 꽂혀 있고(장비당 인터페이스 13~75개), 터미널 `show interfaces descriptions`에서 `장비 고객사 속도`(예: `IDC_B_FS3 가상물산 10G`)로 보입니다. 짝 장비는 같은 고객 회선 목록이 같은 포트로 보입니다. 장비 간 회선에도 속도(100G, 10G ...)가 붙습니다.
- 고객사는 19곳 그대로이고, 큰 고객사 6곳과 서초→분당 회선의 트래픽만 키웠습니다(피크 사용률 60~70%대, 경고선 80% 아래). 기존 8개 회선의 값은 그대로입니다.
- **미사용 회선**: 고객 회선의 약 30%는 아직 쓰지 않는 회선으로, Link down(선만 꽂아 둠) 또는 Admin down(관리자가 내려 둠)으로 표시됩니다. 짝 장비에도 같은 상태가 보이고, 이상(빨강)으로 세지 않습니다. 3D 상세에서는 회색 포트로 보이고 케이블은 그리지 않습니다.
- **장비가 꺼진 상태 반영**: 장비가 꺼진 시간대(데이터의 `down_start`~`down_end`)에는 그 장비의 터미널이 응답하지 않고(접속 시간 초과), 그 장비와 이어진 옆 장비의 포트는 Link down·빛 없음(-40 dBm)으로 보입니다. 서버실·3D에서 장비 터미널을 열 때 지금 보고 있는 가상 시각이 같이 넘어갑니다. 짝 장비는 같은 시간에도 정상입니다.
- **이중화 시나리오**: IDC_B_FS7이 새벽에 꺼져도(전원 모듈 고장 가정) 짝 장비 IDC_B_FS8이 같은 고객 회선을 받아서 큰 장애 없이 넘어가는 과정을 보여 줍니다. 이중화가 없었다면 몇 개 회선이 끊겼을지도 계산해서 보여 줍니다(가정).
- **3D 조작(아이패드 포함)**: 한 손가락 드래그는 '회전/이동' 선택대로, 두 손가락은 확대·축소와 이동입니다. 화면 오른쪽 아래의 큰 버튼(이동·회전·확대, 접을 수 있음)으로도 조작합니다.
- **Cisco = Nexus 7710(추정)**: 업무 메모의 "7710 장비"와 사진의 10슬롯 섀시로 추정했고 모델은 확인하지 못했습니다. 14U, I/O 모듈 8개 + 슈퍼바이저 2개(가운데) 구조로 그렸습니다(높이는 판매처·데이터시트 자료 기준). 포트 이름과 명령 출력은 NX-OS 형식 그대로가 아니라 일반적인 Cisco 형식으로 만든 가상 값입니다.
- **이중화 짝은 다른 랙**: 짝 장비(FS1-FS2 ...)는 서로 다른 랙에 둡니다. A측 랙에 홀수 번호, B측 랙에 짝수 번호를 담아서 한쪽 전기가 나가도 반대쪽이 살려 줍니다(그래서 랙이 44개에서 46개로 늘었습니다). 냉각 이상은 B측 랙 IDC_B_R08(IDC_B_FS6·FS8)에서 일어나고, FS6의 짝 FS5는 다른 랙 IDC_B_R07이라 영향이 없습니다.
